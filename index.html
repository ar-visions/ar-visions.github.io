A native build language whose import is open to the world.

silver compiles .ag source to native binaries through LLVM. One import line clones a dependency, detects its own build system, builds it, and links the result — then live-reloads your running app on every save, with full debugger support on every platform.

Why it's different

An isolated environment, filled with best practice.

No package manager, no binding layer, no vtable tax you didn't ask for, and no platform where the debugger goes dark. The whole ecosystem — from LLVM down to the Au runtime — builds from source in isolation, into one self-contained folder that never touches your system, and your cross-platform apps build from that same SDK.

importDirect from authors

Write import owner:repo/commit. silver clones it, detects CMake, Meson, Cargo, GN, or autotools, builds it with that project's own tools, and links the output. C headers are parsed through libclang and made available at design time.

↻Live reload, built into the app

The source watcher is compiled into the binaries themselves — not bolted onto an editor. Every silver app can watch its own source and rebuild in place, whether you're developing it or it's been installed into share. Edit, save, and the app hot-reloads its main module through a built-in host — no script, no separate binary, not even a window reload. The same Vulkan session stays live while your application module swaps underneath it.

⚙Debug, test, profile — built in

Every build emits full LLDB debug info — source maps, variable inspection, stepping, breakpoints — on Linux, macOS, Windows, and embedded ARM from one source tree. Mark a function expect func and the test compiles into the module itself; silver --test app runs every expect across the module and its imports, constructing the arguments — a live Vulkan context included. A release build runs the debug tests first, and carries no test code at all.

.agiA registry any tool can read

export extensions ['.gen'] in a module writes export/rgen.agi under the silver root at build time — one readable text file per module, keys for whatever the module declares. orbiter opens a .gen by that declaration and runs rgen in its own process. Modules built years apart associate without ever being compiled together.

↔C/C++ with no bindings

Declare a function in silver, implement it in a .c or .cc file beside it. It compiles and links automatically with full access to your fields. The shared object model — Au — serves C, C++, and silver equally.

The module

One module, many languages.

.ag .c .cc .rs css png

A silver module is a directory. Inside it: the .ag source, its .c and .cc companions, the shaders, the stylesheet, the assets — built and versioned as a single unit. Several languages and their resources, bound into one importable thing.

It's a simple idea almost nothing else does: the module is its silver source — the .ag file — together with companion source in C, C++, GLSL, and beyond, imported by name and built for you in full.

The import system

import Built the way the authors intend.

Decentralized by design — depend on a commit or branch for deterministic builds. No insecure supply-chain. Go direct to the software people.

app.ag
import KhronosGroup:Vulkan-Headers/29184b9
import glfw:glfw/fdd14e6 <GLFW/glfw3.h>

import madler:zlib/51b7f2a <zlib.h>

Interoperability

C and C++, sharing one object model.

There is no binding layer because there is nothing to bind. silver, C, and C++ meet inside a single C runtime — Au — where every type is described by one schema node.

Everything is an Au_t

One type descriptor stands behind all of it — structs, classes, enums, and each of their members. An Au_t holds a type's members, methods, vtable, size, and traits. Reflection, reference counting, and single inheritance come from the runtime, not from each language separately.

The schema node

A type is declared once as a schema — its members, methods, overrides, and constructors — and that schema produces the same Au_t whether the type was written in silver or in C. The object layout is identical, so a field is the same field on either side.

Imported at design time

C and C++ headers are read through libclang as you build. Their macros, structs, and functions become Au_t nodes too — a Vulkan handle or a zlib struct is a first-class participant in your program, not a foreign object reached through a wrapper.

image.ag + image.c
# image.ag — declare in silver, leave the body out
class image
    public uri: path
    public w: i32
    public h: i32
    func decode [ ] -> none

// image.c — implement in C, with full field access
none image_decode(image self) {
    FILE* f = fopen(self->uri->chars, "rb");
    // self->w and self->h are the same fields silver sees
    ...
}

# no wrappers, no bindings, no marshalling — it just links

Au_tOne descriptor

Structs, classes, enums, and their members are all the same node. Learn one model, not three.

{ }One schema

The schema generates the C struct and the silver type with one identical layout — so there's no marshalling at the boundary. A field is the same field on both sides.

< >One namespace

Imported C and C++ types are first-class at design time — reflected through libclang, not wrapped.

Cross-platform · Docker integrated

The compiler ships Docker inside it.

Cross-compiling is usually a fragile pile of toolchains. silver folds Docker into the compiler itself: name a target and it builds a per-platform image from that platform's Dockerfile, then runs the entire build inside the container — your dependencies' CMake, Meson, GN, and autotools, then llc, clang, and the final link — against that platform's SDK.

You never touch a container. silver builds the image if it's missing, mounts the SDK, and even negotiates docker permissions on its own. One command, any target:

shell
$ silver --platform linux-aarch64 orbiter
# → builds the image, compiles + links inside it, emits an arm64 binary
# silver [flags] module [app-args] — args after the module go to the app

The language

Succinct and explicit.

Polymorphism you opt into

Calls are direct by default — a static call with zero vtable overhead, so LLVM can inline, const-propagate, and auto-vectorize across the boundary. When you want dynamic dispatch, you ask for it with *. The cost is visible exactly where you pay it.

Units as types, shapes as literals

200px and 200em are distinct types with compile-time conversions. new f32 [32x32x1] allocates a typed tensor. Built for graphics, DSP, and neural nets.

Member access

Less to pass around.

Visibility and context are part of the type, not an afterthought — so the compiler threads the right data to the right place and keeps modules honest.

context — bound from scope, by type

A context member binds automatically to a value of its type already in scope — the Vulkan context, the active window, the allocator. Declared once, present wherever it's needed, and never threaded through every call in between. It's implicit integration of contextual data, and you can always override it explicitly. Less to pass around, more to read.

intern — visible to the whole module

An intern member is internal to the entire module, not just its class — so collaborating types share state without exporting it. That's dependency isolation at the module boundary, and it removes the need for friend-style escape hatches.

expect — the user must provide it

An expect member is part of the public surface, but the compiler won't let an instance exist without it. Omit it at construction and the build fails, naming exactly what's missing — configuration errors caught at compile time, not at runtime. Context members are required the same way.

element.ag
class element
    context vk  : vk_context   # bound from scope, by type
    context ux  : Window       # never passed in
    intern  fd  : i32 -1      # module-visible, not exported
    expect uri : path         # the user must provide this
    public  id  : string       # part of the public surface

    func render [ ]
        vk.begin [ ]            # vk is simply here
        ux.invalidate [ ]

Built in silver

It compiles its own tools.

About a quarter of the codebase — the IDE and the renderer — is written in silver itself. The strongest test of a language is whether you'd build something real in it.

IDE

orbiter

The development environment for silver, written in silver, running on the trinity engine — editing and live-reloading itself.

ENGINE

trinity

A Vulkan-based composition and SDF compute-canvas — the rendering foundation orbiter is built on.

trinity engine

Declarative UX, CSS with your properties.

orbiter — the IDE — is built on trinity: a Vulkan composition engine whose canvas rasterizes vector shapes as signed-distance fields on the compute pipeline. The entire interface is described in a CSS dialect, with layers, transitions, and filters built into the language of the stylesheet.

SDF canvas on Vulkan compute

Rounded rects, paths, and strokes are evaluated as signed-distance fields by a compute shader and written to a storage image, then composited. Crisp at any scale, antialiased for free, and resident on the GPU — no CPU rasterizer in the loop.

Layers, not element trees

A single element carries named render layers — layers.base, layers.inner, layers.border — each with its own area, fill, stroke, and glow. One element does the work of a whole nested subtree, so there's far less for you to declare.

Transitions & low-pass, in the CSS

A property animates by appending its timing: fill_color: #4af, 222ms cubic. Dynamic shader inputs are smoothed by a low-pass filter the same way — pulse_width: 1.0, filter 0.8. Motion and signal-smoothing are declarative, never wired up by hand.

orbiter.css
/* one element, several visual layers — not a tree */
Group / Check {
    layers.base:
        area:         l0.5 t0.5 w1.0 h1.0
        fill_color:   #0004
        stroke_color: #fff4
        radius:       9
    layers.inner:
        fill_color:   #4af0, 222ms cubic   /* transition */
        inner_glow:   #fff0 8, 222ms cubic

:selected
    layers.inner:
        fill_color:   #4af,  222ms cubic
        stroke_color: #fff8
}

import

One keyword, every source.

import resolves a dependency, builds it from source, and brings its types into scope. It has a handful of forms — all of them build, none of them pull a prebuilt binary.

The forms

import img                          # local silver module
import madler:zlib/51b7f2a <zlib.h>   # owner:project/commit + C header
import KhronosGroup:Vulkan-Headers/29184b9
import numpy as np                  # namespaced
import <stdio.h>                    # a C header alone

From anywhere — from

By default an import resolves against your own git service and owner. from overrides that, pointing import at any service or URL — the rest of the line behaves the same.

import mylib from https://gitlab.com/team/mylib/a1b2c3d

It detects the build system

silver clones the repo, recognizes its build — CMake, Meson, Cargo, GN, or autotools — runs it with that project's own tools, and links the result. C and C++ headers are parsed through libclang and made available at design time, macros included.

silver + C + C++, one module

A module's .ag source compiles alongside its .c and .cc companions. Declare a function in silver with no body, implement it in C — they share the Au object layout, so there are no wrappers and nothing to marshal.

class image
    public uri: path
    func decode [ ] -> none      # body lives in image.c

Imports take parameters

Module-scope members are configuration inputs, set by the importer:

import mymodule
    debug:   true
    version: "1.0"

live reload

The watcher ships in the binary.

Run a project in watch mode and silver keeps an eye on its source. On save it recompiles only the changed module, loads the new code, and hands control back — the window and the Vulkan session never tear down.

$ silver orbiter --watch

What persists

A built-in host holds long-lived state — the Vulkan context, caches, your app object — across the swap. Only the application module's code is replaced underneath it, so a reload costs a frame, not a restart. Installed apps under share watch their own source the same way.

debug · test · profile

Instrumented by default.

Debug is the default build. Every binary carries full LLDB information — source maps, stepping, breakpoints, variable inspection — on every platform from one source tree.

Tests live in the module

Mark a function expect func and it becomes a test. No separate harness — it compiles in, with coverage mapping and nanosecond timing reported per run. silver --test app runs every expect across the module and its imports, in each module's own initializer, then exits before the app starts. Arguments are default-constructed — a test taking vk_context receives a real one, renders headless, and reads its pixels back. A graphics app pins the average color of one rendered frame: four integers that move when anything in the render path changes.

expect func math_ok [ ] -> bool
    return add [ 2, 2 ] == 4

A release build runs the debug tests first and refuses to build when they fail — and the release binary contains none of the test code.

C / C++ interop

One object model, no bindings.

silver, C, and C++ meet inside Au — a C runtime with reference counting, reflection, and single inheritance. Every type, in any of the three languages, is one Au_t schema node with one memory layout.

# image.ag — declare in silver
class image
    public uri: path
    func decode [ ] -> none

// image.c — implement in C, full field access
none image_decode(image self) {
    FILE* f = fopen(self->uri->chars, "rb");
}

The schema generates the C struct and the silver type with identical layout, so a field is the same field on both sides — nothing to marshal at the boundary.
