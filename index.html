silver
Imports Live replacement Native code Source

A native language with its build graph inside the source.

A silver module can fetch and build the code it imports, expose native APIs without a binding layer, run typed work during its build, and replace its own running image without restarting the process.

Compilation unit

The folder is the module.

The .ag file defines the module. C, C++, Rust, shaders, styles, images, and other resources beside it belong to the same build and install unit.

There is no second manifest that repeats the source list. A bodyless silver declaration can be implemented in a companion native file. Resource folders are installed under the module's share path. Another .ag file can join the module with extend.

export 1.0.0
export extensions [ '.scene' ]

import <stdio.h>

class Image
    public width : i32
    public height: i32
    func decode [ bytes: @u8, count: i64 ]

# Image_decode may live in the module's .c file.

Exports are written to a plain AGI registry under the installation. Programs can discover file types, launch properties, or other module facts without linking the module that published them.

Dependency builds

import resolves source, build, types, and link input.

An import is a build-graph edge. Its spelling says where the dependency comes from; its indented body says how that dependency is configured and what the importing module consumes.

The forms

import vec
import random with RandomExtra as rng
import <stdio.h, limits.h>

import madler:zlib/51b7f2abdade71cd9bb0e7a373ef2610ec6f9daf <zlib.h>
    -DCMAKE_POLICY_VERSION_MINIMUM=3.5
    -lz

import bzip2:bzip2/66c46b8c9436613fd81bc5d03f63a61933a4dcc3 \
    <bzlib.h> from gitlab

import https://example.org/data/table.bin
    > cp {import_file} {install}/share/app/data/table.bin

A short name resolves a local module or an installed module. A repository name can select an owner, project, submodule, commit, branch, or remote service. from accepts a known service name, a hostname, or a full repository URL. A raw HTTP URL means one file or archive; it is not treated as a repository.

with compiles one or more extension files into an imported silver module. as changes the name used in the importing source. An import of the current repository resolves to the local tree rather than cloning itself.

What happens to a repository import

  1. Resolve.The parser separates the remote, owner, project, selected module, revision, headers, and local configuration.
  2. Acquire.A full 40-character commit is fetched shallowly into a detached checkout. A branch is cloned shallowly. Short hashes use history because Git cannot fetch them by object ID. Submodules are initialized recursively.
  3. Apply local changes.A sibling .diff is applied once. A same-named overlay folder is copied over the checkout on every build; a .deleted list removes upstream files.
  4. Select the native build.The checkout is inspected for CMake, Meson, GN, Cargo, a configure script, or a silver module. Builds run outside the source tree.
  5. Install into the selected prefix.Native dependencies build as release artifacts. Cross-target builds receive target-specific CMake and Meson toolchain files and install under the target's own prefix.
  6. Read the interface.Headers are parsed with libclang. Functions, records, typedefs, constants, macros, namespaces, and C++ templates enter silver's type graph. Libraries and frameworks named in the import are added to the final link.

The indented body has defined roles

Build arguments

Ordinary tokens are passed to the selected build system. The configuration is part of the cache identity.

Environment

NAME=value lines reach configure and build commands and also take part in the cache identity.

Consumer inputs

-I, -l, framework names, bare -DNAME, and silver defines marked with +NAME=value feed the importing module.

Commands

> runs in the checkout before the normal build. >> runs against the installed tree, including on a cache hit.

Configuration may be conditional on platform or another define. A module import may instead use name: value fields; those are read-only parameters inside that module.

The cache is based on build meaning

The build stamp includes the configuration, environment, compiler choice, C++ include mode, selected submodule, and every pre-build command. A changed overlay is detected separately. Concurrent silver processes take an exclusive lock per dependency, so one checkout is not erased while another process is compiling it.

Direct URL downloads use a URL hash in the filename. They are first written to a partial path and renamed only after a successful fetch, so a failed transfer cannot become a valid cache entry.

Revision choice remains visible. A full commit gives a pinned source state. A branch intentionally follows that branch. The import line records which one the build asked for.

Implementation: import parser and build graph. Executed examples: module tests.

Live replacement

The process stays up while the application image changes.

On the desktop host, the application module is a loadable native image. The host owns the frame loop and watches the exact source and generated artifacts recorded by the last build.

From an edit to a new frame

  1. Detect the edit.Each build writes a source manifest. The host compares those files with the current product and notices external rebuilds as well as direct source changes.
  2. Compile without stopping the app.The build runs in another process. The old image keeps handling input and drawing frames. A compile error is reported, but the last good image remains live.
  3. Load a distinct image.The product is copied to a unique temporary inode before dlopen, avoiding the loader's same-inode cache. On Windows, copying also avoids holding the product DLL open while the linker writes its successor.
  4. Initialize beside the running instance.The new module starts on a worker thread in a separate Au type space. Its types do not replace the live registry while initialization is still in progress.
  5. Switch on a frame boundary.The host hands off frame-owned work, pauses callbacks into the old image, removes the old module from the type registry, promotes the prepared type space, and points the frame loop at the new entry points.
  6. Retire the old image safely.Destruction runs on a worker. The host waits for async work still executing old code, drains reference-counted objects while their type code remains mapped, then closes the old library.

The new instance can render before the handoff while the old instance still presents. In Trinity applications the window, graphics device, swapchain owner, and host microphone are outside the replaced module. The new instance initially defers taking the swapchain and adopts it at the switch.

State has explicit routes across the boundary

persist reloads: i64 [ 0 ]

app Example
    func init []
        reloads += 1

A persist slot is held from the old image, loaded into the new image before initialization, and released from the old slot after promotion. Its type cannot be defined by the module being unloaded; otherwise the value would outlive its own type code.

Application frameworks can carry richer state through their own stable owner. Trinity keeps the window and display objects outside the replaceable image and lets the new instance adopt visible state. An app can also save reload-specific state during destruction; the host marks reload teardown separately from final process exit.

Automatic or staged

The host can build and apply immediately, or stage the change. In staged mode the application sees four useful states: unchanged, waiting for approval, compiling, and ready to switch. This lets an editor or a full-screen application choose the exact handoff moment and finish a visual transition first. Externally produced builds follow the same staging path.

The boundary is enforced

Only the application image is replaced. If a loaded silver dependency has been rebuilt since process start, the host refuses the swap and asks for a restart; continuing with the old dependency image and a new layout would be unsafe. A torn library copy is retried. A failed load leaves the current instance running.

Platform scope. This path is used by the desktop live host. Sealed iOS and Android packages load their application image once and do not offer live replacement inside the installed package.

Implementation: desktop host, generated live entry points, and persist validation.

Runtime type graph

Types are available as data.

Each module, class, struct, enum, member, method, constructor, cast, operator, getter, and setter has an Au_t descriptor. Compiled code and runtime tools read the same graph.

typeid accepts a static type or a value. Runtime checks can compare exact identity or walk inheritance. Members are searchable by name and kind, including non-public members when the caller has the module context.

class Range < string >
    public [ Launch, Slider [ 0.0, 1.0 ] ] value: f32
    action func reset []
        value = 0.0

t: Au_t [ typeid[ Range ] ]
m: Au.find_member[ t, 'value', AU_MEMBER_VAR, 0, false ]
Metadata
A type and each member can carry one or two typed metadata objects. Tools can find controls, launch fields, shader bindings, or other interfaces without a parallel schema.
Actions
An action func is marked as a host-callable operation. It remains an ordinary typed method when called by silver code.
Attributes
attrib creates a static declaration-time object. Its value is available through the member descriptor.
Serialization
AGI writing and parsing use the graph. The tests round-trip nested structs, vectors of objects, Unicode field names, null fields, and ordinary scalars.
Arguments
The command-line reader maps --name value to public members and the bare argument to the member marked default.
Registry
Module exports are written as AGI. A process can find a module by name at runtime; live replacement removes the old descriptors and promotes the prepared descriptors at the handoff.
Object model

Dispatch is a call-site decision.

Class methods call directly by default. Add * when the call must follow the runtime type.

class Shape
    public sides: i32
    func name [] -> string [ 'shape' ]

Shape Triangle
    sides: 3
    func name [] -> string [ 'triangle' ]

base: Shape* [ Triangle [] ]
static_name: base.name[]
dynamic_name: base.name*[]

The direct form preserves a visible, optimizable call target. The dynamic form uses the object's runtime type. super reaches the base implementation. Abstract classes and abstract members enforce that a concrete subtype supplies the missing behavior.

Member declarations carry policy

public / mutable

Public read access, with external writes enabled only for mutable members.

intern

Visible to cooperating code in the module, absent from the exported interface.

expect

Required construction input. Construction fails when the value is missing.

context

Bound by type from an existing context instead of threaded through every intermediate call.

manual / unmanaged

A raw object slot that does not take or release a reference.

static / persist

One slot per type, with persist adding transfer to the next live image.

Classes support typed constructors, post-construction conversions, init, operators, casts, getters, setters, and indexers. A change block under a member runs after later stores. Method declarations may keep their signatures in the class while placing the body elsewhere as func Type.method.

Data and numeric model

Layout and units remain in the type system.

Structs use native C layout and pass by value. Vectors are typed contiguous storage. Scalars attach a unit to a number, and shapes attach dimensions to storage.

Value types follow the ABI

struct v2
    x: f32
    y: f32

    operator + [ b: v2 ] -> v2
        return v2 [ x: x + b.x, y: y + b.y ]

    func dot [ b: v2 ] -> f32
        return x * b.x + y * b.y

A struct can be built positionally or by field name and can define methods, operators, and conversions. Values move correctly through local arrays, vectors, pointers, object members, nested calls, and native function returns. Small and large return values use the target's normal C ABI.

Units are distinct scalar types

scalar mm: f32
    cast -> cm [ a / 10.0 ]
    construct [ v: cm ] [ v * 10.0 ]

distance: 254mm
width: 200px
delay: 16ms

A scalar can define construction and casts between units and can override its text form. Integer-backed units reject fractional values. Arguments written without commas can be matched by type, so distinct unit types can determine their own parameter positions.

Shapes and vectors

a: vec f32 [ 2x2 ] [ 1.0 2.0, 3.0 4.0 ]
b: vec f32 [ 2x2 ] [ 5.0 6.0, 7.0 8.0 ]
c: a * b
d: sqrt[ a ]
cell: a[ 1, 0 ]

A shape is itself a value with a dimension count and total size. Shaped vectors accept one index per dimension. Arithmetic is element-wise; scalars broadcast; numeric built-ins such as square root, min, max, and clamp map over vectors.

local T[n]
Fixed or runtime-sized stack storage with direct address access.
vec T[n]
Contiguous typed storage. Initial capacity is inline; growth moves elements to a heap allocation without changing vector identity.
vec T[]
A growable vector. Push, insert, shift, pop, remove, reverse, concatenate, search, clear, and element-wise conversion are built in.
map V[K]
A typed map whose bracketed type is the key. Its initial hash size can be specified, and iteration yields value then key.
Ownership and concurrency

Reference changes are observable.

Class objects are reference counted. Ordinary object members hold their value; manual members and raw pointers do not.

n: i32 [ 41 ]
p: @n
p[ 0 ] += 1

func bump [ value: ref i32 ]
    value[ 0 ] += 1

bump[ @n ]

@value takes an address. @Type declares or converts a typed pointer. Pointer arithmetic is measured in bytes. Vectors passed to native pointer parameters expose their element storage rather than the vector object.

Closures own their context

func mul_add [ a: i64, b: i64 :: base: i64, scale: i64 ] -> i64
    return (a * b + base) * scale

base: 10
scale: 2
work: lambda mul_add[ base, scale ]

The arguments after :: become explicit context. Inline lambdas infer and copy their captures at the point where the lambda is made. A lambda stored in a member holds that context past the creating stack frame and releases it when the lambda is freed.

Async work uses the same closure model

An async object applies a work lambda to a vector of objects on worker threads. Captured objects remain held for the work, and sync[ null ] joins it. The live host also tracks workers by image, which is why a module is not unmapped while one of its async callbacks can still run.

The memory tests capture and touch a 10 MB object, drain the automatic object pool, verify that the closure released it, and check that the resident memory returned. The suite also records the live-object count at its first test and compares the final count after a full drain.

Native code

C, C++, and Rust use the same memory.

Companion source is compiled with the module. Imported headers become typed silver declarations at design time.

C is direct

C integer spellings, records, typedefs, fixed arrays, function pointers, varargs, constants, and macros are usable as declared. A silver string crosses to a C string where required. C can write into a silver local array or vector through its native address.

intern func c_fill [ @i32, i32, i32 ]

values: local i32 [ 4 ]
c_fill[ @values[ 0 ], 4, 10 ]

C++ keeps its language surface

Classes retain overloaded constructors, methods, operator overloads, and conversion operators. Namespaces remain qualified. Type templates, integer template arguments, multiple template parameters, and namespaced function templates are supported.

pair: pairT<i64> [ a: 40, b: 2 ]
scaled_value: scaled<i64,6> [ v: 7 ]
clamped: std::clamp<i32>[ 7, 1, 3 ]
rect: geo2::rect2 [ ]

If a required specialization is absent from the header's explicit instances, the import translation unit requests it when silver source first uses that type.

Rust and inline assembly

A Cargo import builds the release crate into the selected target prefix and uses cbindgen for its external C surface when available. A module's Rust companion reads and writes the same buffers used by silver and C++. Architecture-gated assembly supports x86-64 and ARM64, including typed expression results returned from a named register.

Design-time execution

Typed code can produce part of the build.

export func runs after module initialization during the build. It can generate an artifact with the same language and types used by the application.

export func bake_table []
    output: path '{path.path_share_path[]}/data/table.txt'
    output.save[ make_table[], null ]

The tested pattern hashes the source token of the producer, compares that stamp with the installed artifact, and runs only when the producer changed. silver --export forces the export path when a fresh artifact is required.

A configured coding agent can supply a function body

func gcd [ a: i64, b: i64 ] -> i64 using claude
    { Euclid's greatest common divisor; either argument may be
      negative or zero, and the result is never negative }

The author owns the signature, types, and prompt. The generated body is saved under the module's gen folder and compiled as ordinary silver. It is reused while the signature and request still match.

The feature suite exercises generated arithmetic, branches, loops, string algorithms, instance methods, tests, image inspection, generated image resources, and build-time file generation. The generated code receives no alternate runtime or type privileges.

Verification

Tests are members of the module.

expect func declares executable test code beside the feature it checks. silver --test discovers those functions through the module type graph and runs them in definition order.

expect func t_vector_math [] -> bool
    a: vec i32 [] [ 1, 2, 3 ]
    b: a * 2
    expect b[ 2 ] == 6, 'last value is {b[2]}'
    return true

expect also works as a statement or expression inside normal code. It may bind the checked value and attach a diagnostic. check raises a catchable failure; fault stops immediately. A test declared inside a class receives a new default instance.

The main feature suite contains 275 executable tests covering the language, imports, native interop, code generation, build-time output, serialization, memory accounting, and ABI behavior. The page links to that suite because it is the exact source behind the examples.

Language surface

Core syntax, in one place.

Square brackets hold calls, conditions, constructors, and index operations. Indentation forms statement blocks. Braces hold uninterpreted token or text blocks.

Flow
if / el, while loops, one-, two-, and three-part for loops, do-while form, forward and reverse collection iteration, numbered break and continue, and non-falling switch over enums, integers, or strings.
Errors
try, typed or untyped catch, finally, and throw. Finally runs on normal completion, caught failure, and rethrow.
Expressions
Arithmetic and bit operators, compound assignment, inclusive and exclusive ranges, match lists, null coalescing, conditional values, three-way comparison, source location values, and numeric math that maps over vectors.
Text
Single-quoted interpolated strings, double-quoted C strings, Unicode character literals, C-style numeric formatting, dedented multiline string blocks, compact command blocks, and path operations.
Names
Unicode identifiers are accepted and normalized to NFC, so composed and decomposed spellings resolve to the same symbol.
Conditional source
Platform and architecture names are boolean values. ifdef and ifndef gate imports or statements, with ordinary el branches.
